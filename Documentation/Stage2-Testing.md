每完成一个 Stage 2 实施步骤，从仓库根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\stage2-test.ps1
```

入口重新编译带 Shell 命令通道的普通内核镜像，不使用 SELFTEST 内核，不复用上轮通过结果。测试以命令输出、用户态自检、资源账目和持久化字节为依据。G1增加真实QMP键盘、焦点、文本场景和一次简单最大化按钮检查，继续排除复杂缩放、拖动和像素比对。无需关闭正在运行的日常开发 VM，测试不使用它的磁盘；同一源码目录的构建锁覆盖整个测试过程。

这里将“排除画图、文本文档”解释为排除画板和 GUI 文本编辑器的业务测试。文件系统的文本/二进制读写、Shell 重定向与保存仍属于底层基础能力，继续覆盖。

## 前置条件

使用现有 Node.js、支持 32 位目标的 GCC/Binutils、Python、仓库 NASM 和 QEMU。工具查找沿用原开发入口；必要时设置 SINO_TOOLCHAIN、SINO_PYTHON、SINO_QEMU_DIR。本集不需要 Pillow 或额外测试框架。

普通/测试镜像与原有 22 组 GUI/系统回归仍有自己的使用规则，见 [testing.md](../Source%20Code/docs/testing.md)。本入口独立运行，不能把它的通过结果记为完整 22 组门禁通过。

总报告中的 runner-rejects-failure 应为 PASS，其子报告应为 FAIL；这是对失败检测能力的检查，不是忽略实际回归。任何其他失败原因、启动失败或 VM 未清理，都不能让这一分组通过。


## 它证明什么，以及还不能证明什么

该集验证现有能力的行为基线，并已覆盖 A-E 的最小查询/严格策略、完成对象、有限标准流、授权文件对象、有界管道和运行库等待。它不代表完整 SpawnEx、线程级阻塞等待、任意长度原生管线或通用委托已经实现。新接口每落地一项，都应将它的正反例加入本集，并更新完成标准。

目前 Shell run 只返回启动结果。原生自检会等待本轮新日志、确认对应 PID 已回收、检查正常退出/故障计数与资源；不把启动成功当成程序测试成功。但这仍不是未来可保留、可直接读取最终退出码的 wait 契约，必须继续建设完成对象。

大部分测试运行本轮重编译的程序，不能单独证明任意历史 SNX 的二进制兼容性。修改 ABI 编号、布局或旧接口语义前，应加入相应旧二进制固定夹具，并以原封不动的旧程序验收；不能靠同时重编内核与应用掩盖不兼容变更。

固定表和结构布局的私有检查适配器如果失效，会明确失败并要求检查，不自动猜新偏移。限额测试中的 8 个进程、24 个句柄、64 KiB 文件是当前基线；有意改变限制时，应一并审查契约与测试。不能为通过测试而随意降低检查要求。

## 底层与接口层如何分步开发

不建议建立第二套内核或复制一套文件系统。保留原应用和旧 ABI，新接口在其旁边增加，由薄适配层调用同一套受测核心实现；旧接口保持原返回值和权限行为，严格权限模式由可信启动者按进程设置。

内存与 VFS 不必“全部完善”才建设接口。先确保已有分配/释放、边界、失败回滚与资源回收可信；每个接口只补它当下需要的能力。例如完成对象先建立有界记录，不要求先有通用用户堆；标准流先使用有限捕获，不要求先有完整文件流或 TTY。

接口边界可以减少相互影响，不能消除共享实现的影响。更换页分配器、VFS 或提交路径仍可能影响所有调用者，所以每一步运行本集。旧软件要等替代功能与数据兼容得到验证后再迁移或退役，不以先删除旧软件来回避兼容问题。
